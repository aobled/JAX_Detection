- (note) Contexte : domaine chess_ai (projet séparé de jax_supervised_training) — modèle ChessCnnAttentionPolicyValue (model_library.py:837), checkpoint best_model_chess_search_teacher.pkl, config CHESS_SEARCH_TEACHER (token_dim=192, num_bottleneck_tokens=16, Val PolicyAccuracy 28.00%).
- (decision) Intent central : geler tout le modèle (backbone CNN, projections d'attention Wq/Wk/Wv/Wo, têtes policy/value, batch_stats) et ne faire évoluer que params["bottleneck_queries"] (array (16,192)=3072 floats) via algorithme génétique.
- (capability) CAP-1 — Représentation d'un individu : checkpoint export pur standard (params/batch_stats/config) identique au checkpoint de base sauf params["bottleneck_queries"] substitué. Success : compatible tel quel avec load_chess_model/select_model_move existants (chess_model_inference.py), aucune modification de ces fonctions.
- (capability) CAP-2 — Identification d'individu par hash de contenu : caster bottleneck_queries en float32, np.ascontiguousarray, sha256(arr.tobytes()).hexdigest()[:12]. Success : ID stable et reproductible pour un même génome, sert de dédup pour sauter la réévaluation d'un génome déjà rencontré dans une génération antérieure.
- (capability) CAP-3 — Initialisation génération 0 : population de 20 individus = checkpoint actuel + 19 mutations gaussiennes (pas d'init aléatoire from scratch). Success : les 20 checkpoints se chargent sans erreur via load_chess_model.
- (capability) CAP-4 — Opérateur de mutation : bruit gaussien additif sur les 3072 floats, amplitude mutation_sigma paramétrable. Success : mutation_sigma=0.01 par défaut (grounded sur l'écart-type réel mesuré 0.0877 de bottleneck_queries dans best_model_chess_search_teacher.pkl, 2026-08-09 — soit ~11% de l'échelle actuelle), ajustable sans modifier le code.
- (capability) CAP-5 — Sélection : score cumulé par individu sur le round-robin, système points échecs (victoire=1, nulle=0.5, défaite=0), conserver les 10 meilleurs sur 20. Success : classement reproductible à partir des résultats bruts du tournoi, jamais un simple compte de victoires.
- (capability) CAP-6 — Opérateur de croisement : uniforme ligne-à-ligne — chaque ligne (192 floats) du tableau (16,192) tirée 50/50 chez l'un ou l'autre parent, indépendamment par ligne. Success : les 10 survivants produisent 10 nouveaux individus (mutation + crossover combinés) pour reformer une population de 20.
- (decision) Crossover choisi = uniforme ligne-à-ligne, PAS single-point/segment contigu — les 16 lignes n'ont aucune relation de localité entre elles (modèle invariant à leur permutation : auto-attention équivariante + mean pool invariant en aval), donc aucune raison de préserver des blocs contigus comme le ferait un GA classique sur chromosome ordonné.
- (capability) CAP-7 — Évaluation de fitness : round-robin N-way construit au-dessus de tournament_model_vs_model.py (actuellement pensé pour 2 modèles), réutilisant play_one_game/random_opening_moves tels quels sans les modifier. Success : games_per_pair=4 (2 ouvertures × 2 couleurs, cohérent avec la contrainte existante n_pairs=games//2) × C(20,2)=190 paires = 760 parties/génération ; paramétrable, augmentable si le signal est trop bruité.
- (capability) CAP-8 — Départage des nulles : score Sonneborn-Berger (pondéré par la force des adversaires rencontrés) calculé en post-traitement des résultats du round-robin, zéro infra supplémentaire. Success : classement différencié même sur une génération majoritairement nulle.
- (assumption) La tête value NE PEUT PAS servir de départage : vérifié directement dans best_model_chess_search_teacher.pkl (2026-08-09) — loss_params.value_weight=0.0, value_head_trained=False, sorties = bruit d'initialisation jamais entraîné sur ce dataset.
- (note) Option de repli différée (hors POC) si Sonneborn-Berger insuffisant : réutiliser centipawn_eval/resolve_stockfish_path déjà présents dans evaluate_model_vs_stockfish.py pour évaluer qui poussait un avantage dans les parties nulles.
- (capability) CAP-9 — Mini-pilote de validation préalable : avant tout investissement dans la boucle complète, quelques générations légères doivent valider que mutation_sigma=0.01 produit des parties décisives (pas 100% nulles). Success : taux de parties décisives mesuré ; si nul même à sigma raisonnable, l'hypothèse que bottleneck_queries porte assez le "style de jeu" est invalidée tôt, avant 50 générations de calcul perdu.
- (capability) CAP-10 — Boucle générationnelle : critère d'arrêt = n_generations paramétrable. Success : la boucle s'arrête proprement après n_generations, chaque génération journalisée (scores, IDs, meilleur individu).
- (constraint) Ne jamais modifier chess_model_inference.py::select_model_move ni tournament_model_vs_model.py::play_one_game/random_opening_moves — réutilisation stricte (AD-18 chess_ai, source unique de vérité pour légalité/sélection de coup).
- (constraint) games_per_pair doit rester un nombre pair (contrainte héritée : n_pairs = games // 2 dans le script de tournoi existant).
- (constraint) ID d'individu = hash de contenu (sha256 tronqué à 12 hex) sur les bytes float32 C-contiguous de bottleneck_queries — jamais un compteur/UUID arbitraire, pour permettre la dédup inter-générations.
- (constraint) Sélection par score cumulé (victoire=1/nulle=0.5/défaite=0) obligatoire, pas un compte brut de victoires — sensible aux nulles qui domineront tôt dans le run.
